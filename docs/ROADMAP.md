# EasyCode 开发路线图

## 1. 路线图原则

EasyCode 采用纵向切片推进：每个里程碑只增加一组可独立验收的能力，并保持核心逻辑可由 fake 在离线环境复现。后续里程碑不得以“顺手实现”为由提前进入当前范围。

里程碑状态：

- **M0：已完成**，工程与治理基线已由本里程碑验证命令确认。
- **M1：已完成**，八个 Agent Loop 核心场景已由确定性单元测试覆盖。
- **M2：已完成**，OpenAI-compatible 流式适配与异常边界已由本地 fixture 和离线集成测试覆盖。
- **M3：已完成**，五个受控代码工具及 Agent 离线闭环已由临时 workspace 测试覆盖。
- **M4–M7：未开始**，只保留范围与验收入口。

## 2. M0：工程基线

目标：让独立仓库具备清晰的工程契约、最小 TypeScript 工具链和可持续验证入口。

范围：

- 中文协作约定、架构、设计决策、路线图和验收文档；
- Node.js >= 22、npm、TypeScript strict、ESM、Vitest 与最小 lint；
- `agent`、`llm`、`tools`、`config`、`ui`、`tests`、`evals` 目录边界；
- Message、ToolCall、ToolResult、AgentEvent、Provider、Tool 等类型级契约；
- scripted Fake Provider 及其确定性单元测试；
- 无密钥、无网络调用的基础 CI。

明确不包含：真实 Agent Loop、HTTP 请求、本地文件工具、命令工具、Ink 界面、真实模型测试。

完成标准：所有 M0 文件可审查，`npm run check` 通过，依赖树不含禁用框架，Git 工作区干净并形成单一基线提交。

## 3. M1：可验证的 Agent Loop

目标：只依赖 fake 完成最小自主循环，使核心行为在无网络环境下完全可测。

范围：

- Agent Loop 状态机、step 计数、`maxSteps` 与 abort；
- 流式文本与 ToolCall 组装；
- 工具注册表和 fake Tool；
- 上下文追加、工具结果回传和结构化终止原因；
- `docs/ACCEPTANCE.md` 中八个核心场景的自动化测试。

完成标准：八个场景全部由单元测试确定性覆盖；不接真实 API，不执行真实本地命令。

## 4. M2：OpenAI-compatible Provider

目标：用一个薄适配层连接 OpenAI-compatible 流式 API，同时保持 Agent 核心不依赖厂商 SDK。

范围：

- 环境变量读取与启动前校验；
- `fetch` 请求、流式响应解析、ToolCall 增量归一化；
- 鉴权、限流、网络、协议和取消错误分类；
- 基于 fixture 的协议解析测试；
- 一个可手动启用、默认不进入 CI 的最小真实 API smoke test。

完成标准：Provider 适配层可替换，fake 测试继续通过，日志和异常不泄露密钥。

## 5. M3：最小代码工具集

目标：让 Agent 在受控 workspace 内完成“观察—修改—验证”的最小闭环。

范围：

- 列举/搜索文件；
- 读取文本文件并限制大小；
- 基于明确 patch 的文件修改；
- 受控命令执行，包含 cwd、timeout、abort、输出上限和退出状态；
- 路径穿越、仓库外访问、无效参数和危险操作测试。

完成标准：工具均先校验后执行，集成测试只操作临时 workspace；不提供任意 shell 字符串透传。

## 6. M4：中文 Ink TUI

目标：提供简洁美观的中文终端交互，并保持 UI 与 Agent 核心解耦。

范围：

- 输入区、流式回答区、工具执行状态和错误/终止提示；
- Ctrl+C 取消当前运行，二次退出策略；
- 长输出折叠或摘要、稳定滚动与窄终端降级；
- UI 仅消费 `AgentEvent`，不直接访问 Provider 或工具。

完成标准：关键状态有组件测试或可重复演示步骤；关闭颜色后信息仍可理解。

## 7. M5：安全性与可恢复性

目标：补齐实际使用所需的失败处理和操作边界，而不是扩充功能数量。

范围：

- 统一错误分类与中文可操作提示；
- Provider 可配置重试、退避和幂等边界；
- 工具输出截断、日志脱敏与敏感字段过滤；
- 对覆盖、删除、发布等高风险动作的确认门；
- 中断后资源清理和一致状态测试。

完成标准：已知失败模式不导致静默继续、重复危险执行或密钥泄露。

## 8. M6：评测与可观测性

目标：用可复现证据衡量核心任务质量与成本，而不是依靠演示印象。

范围：

- 固定 fixture repository 与代表性 coding 场景；
- 成功率、工具调用数、模型轮次、耗时和终止原因；
- 代码 revision、Node/依赖版本、模型、参数、命令与原始结果记录；
- fake 回归测试与可选真实 Provider 评测分离。

完成标准：评测可由另一位开发者按文档复现，失败案例保留原始证据。

## 9. M7：交付加固

目标：形成可供考核和演示的稳定版本。

范围：

- 安装、配置、使用、安全边界与故障排查文档；
- Windows、macOS、Linux 的最低兼容性检查；
- 依赖许可证与供应链复核；
- 演示任务、验收清单、已知限制和版本说明；
- 从空环境按锁文件安装并完成全量检查。

完成标准：核心场景通过，有可复现演示，仓库不含密钥或运行残留，已知限制明确。

## 10. 第一版主动排除项

以下能力不进入第一版，除非考核硬约束后来明确要求：

- 多 Agent 协作、角色编排和任务图；
- 自主联网搜索、浏览器自动化和远程 MCP 生态；
- 插件市场、动态加载第三方工具和脚本扩展系统；
- IDE 扩展、桌面 GUI、Web UI 和移动端；
- 远程容器/虚拟机沙箱与云端任务队列；
- 长期记忆、向量数据库、RAG 和跨设备同步；
- 自动 Git push、PR 创建、部署、发布或账号操作；
- 多 Provider 同时路由、自动选模和成本优化器；
- 语音、图片、多模态输入；
- 完整终端模拟器、后台守护进程和多人协作权限系统。

这些排除项不是对长期方向的否定，而是为了保证第一版在截止时间内把自主循环、工具安全、中文体验和可验证性做好。
